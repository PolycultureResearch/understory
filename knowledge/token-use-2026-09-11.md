# Token use in the first live eval

Polyculture Research | September 11, 2026

Where the OpenRouter budget went during the first live evals of Understory, and what to do about it. Companion to `first-live-eval-2026-09-11.md`, which covers what the evals found.

## What was spent

The eval reports recorded no token usage because of a bug in the harness's usage capture, so per-request tokens below are estimates from measured payload sizes at about four characters per token. The dollar figures come from OpenRouter's key endpoint.

| Item | Value |
|---|---|
| Spent on the key on September 10 and 11 | $5.48 |
| Key limit | $10, but the account balance ran out first, which caused the HTTP 402 errors |
| Agent runs that completed | about 85: 47 in the first eval, about 35 in the rerun before credits ran out, 2 live tests, 3 demo questions |
| Cost per question | about 6 cents on Claude Sonnet 5 through OpenRouter |
| Tool calls per question | 3.0 on average, plus one final request each |
| Wall time per question | 16 seconds on average |

Model pricing on OpenRouter at the time, per million tokens:

| Model | Input | Output | Cache read | Cache write |
|---|---|---|---|---|
| Claude Sonnet 5 | $2.00 | $10.00 | $0.20 | $2.50 |
| Claude Haiku 4.5 | $1.00 | $5.00 | $0.10 | $1.25 |
| Claude Opus 5 | $5.00 | $25.00 | $0.50 | $6.25 |
| GPT-5 mini | $0.25 | $2.00 | $0.025 | none |

## Where each question's tokens go

Every request re-sends the whole conversation, so input tokens grow with the square of the number of tool calls. A typical resolved question makes three tool calls and one final reply, so four requests. The model sees about 16,000 input tokens across them and produces about 800 output tokens. Input is 80% of the cost.

The fixed prefix dominates each request. Measured on the alpenglow tenant:

| Payload | Size | Tokens (est.) | Share of a request |
|---|---|---|---|
| get_context result | 7.6 KB | 1,900 | 35 to 40% |
| Seven tool schemas and descriptions | 4.8 KB | 1,500 | 30% |
| System prompt | 2.0 KB | 500 | 10% |
| One query_metrics result, 3 rows | 2.8 KB, of which 1.5 KB is compiled SQL | 700 | 15% |
| Dialog, tool-call arguments, log_answer | | | 10 to 15% |

For reference, a query_metrics result at the 200-row cap is 13.3 KB, about 3,300 tokens, and stays in the conversation for every later request.

Two structural costs sit on top of that:

- The same 3,900-token prefix is sent three or four times per question and is never cached. Anthropic prompt caching through OpenRouter needs explicit cache breakpoints, which the harness did not set.
- Clarification questions cost double. The second turn started a fresh agent run that fetched get_context again instead of continuing the conversation.

## Opportunities, ranked by savings per hour of work

1. **Prompt caching.** Cache reads cost a tenth of fresh input. The repeating prefix is about 70% of input tokens. Expected effect: input cost down roughly 60%, so a question goes from about 6 cents to about 2.5 cents.
2. **Continue the conversation on clarification.** Pass the first turn's message history into the second run. Halves the cost of every clarification item, a third of the golden set.
3. **Cheaper model for routine evals.** The design already treats the harness score as a floor for the client's chatbot. Haiku 4.5 is half the price of Sonnet 5 and GPT-5 mini is eight times cheaper on input. Run the cheap model on every deploy and Sonnet weekly.
4. **Trim the payloads.** Drop the full dimension list from get_context, which is what pushed it past the design's 3 to 6 KB target. Return compiled SQL only on request. Lower the row cap for chat.
5. **Fewer redundant calls.** In 11 of 47 items the model called list_metrics right after get_context, which already lists every metric. The tool description can say so.
6. **Budget guards.** Check the key's remaining limit before an eval, stop on the first 402, and default concurrency to 1. Four tenants at concurrency 3 was 12 parallel conversations, which is how the balance went from fine to zero inside a minute and left four partial reports that cannot be compared.
7. **Fix usage capture.** One function. OpenRouter also returns cost per request when asked, so every report can carry real dollars.

Items 1, 2, 6, and 7 are being built on the `harness-cost` branch. Items 3, 4, and 5 are in the roadmap under 1.7.

Together, the first four take a Sonnet question from about 6 cents to under 2, and a Haiku question to well under 1. A full four-tenant eval then costs under a dollar rather than about three.

## Why this matters beyond the eval budget

In production the client's chatbot pays these tokens, not Polyculture, and the same prefix bloat applies there. The payload trimming and the redundant-call fix lower the client's bill and the latency their employees feel on every question. That is the stronger reason to do them.
