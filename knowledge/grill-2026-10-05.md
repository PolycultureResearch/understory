# Grill before friendly users: where the confidence claim holds and where it is a request

2026-10-05. A critique of the whole build at the point steps 1 to 7 are merged
and the next move is friendly users on a fake tenant. Read: the server, traps,
guard, telemetry, the backlog marts and the findings notes. Run: a probe
against the alpenglow fixture through `Service` directly, with no model in the
loop. Nothing here was run through a real connector or on BigQuery; the items
that rest on reading alone say so.

## Intent against implementation

The deterministic core matches the design. The trap matcher is careful, the
volume check's three rules each have a false positive behind them, and the log
is write-only as designed.

The drift is in where the effort went. The harness and evals are about 3,600
lines against about 1,400 for the server, and the BYO connector path that real
users will hit is the least exercised part of the system.

## Where it breaks

### Traps fire on `spec.question`, which the model writes

`MetricSpec.question` is optional (`types.py:117`) and the matcher reads the
trap phrases from it and nowhere else. The server never sees the user's words,
only the chatbot's copy of them. The probe sent `gross_revenue` for Q1 2025
four ways:

| question sent | result |
|---|---|
| "what was revenue in Q1 2025" | swapped to net revenue, disclosed |
| omitted | gross revenue, no disclosure |
| "gross revenue Q1 2025" (a paraphrase) | gross revenue, no disclosure |
| "and split that by country" (a follow-up) | gross revenue, no revenue disclosure |

`margin_rate` with no question skips alpenglow's one `ask`, the trap the data
owner signed off on because the two margins had been confused in board decks.
The same holds for the unanswerable list: a question the model rewords past
"ltv" is not refused.

All 144 golden items are single-turn, so the follow-up case is unmeasured. The
live evals do cover paraphrase on a first turn, on Sonnet and Haiku, under a
tool docstring that asks for the question verbatim.

### `log_answer` rejects ordinary analysis and passes what it says it checks

- A draft giving January and February net revenue plus the change came back
  `unsourced_numbers` for `-4.7%` and `-46,424`. Both are arithmetic over two
  sourced numbers. The fix instruction then tells the model to rewrite so every
  number comes from a result, which means removing them. Every comparison
  question hits this.
- Status ignores disclosures (`session.py:224`). A draft with a causal claim
  and none of the owed disclosures returned `pass`. The tool description says
  the check covers required disclosures.
- `Session.disclosures` only grows. From the second question on, the missing
  list carries every earlier question's disclosures and is noise.

### Sync work runs on the event loop

The tools in `mcp.py` are `async def` and call `Service` directly. A query at
the 60 second timeout, or a cold `mf` compile, stalls every user of that
tenant, since a tenant is one process.

### `run_sql` scope is wider than it reads

- `select email from main_marts.dim_customers` ran. The scope is the whole
  schema, not the relations behind metrics, and `deny_relations` is empty on
  the fixtures.
- `duckdb_settings()` and `duckdb_tables()` ran, and `enable_external_access`
  is on. The defence against file reads is a list of function names, which has
  to keep up with DuckDB.
- The schema check does not look at the catalog part of a three-part name. On
  BigQuery that is the project, so only IAM stops a same-named dataset in
  another project.
- `BigQueryConfig` has no `maximum_bytes_billed`; the adapter reads it with
  `getattr` and gets None. Model-written SQL is uncapped on cost.
- `daily_counts` is an unbounded group-by over the whole table, run again every
  five minutes per time dimension, inline on the first query that needs it. A
  table that requires a partition filter would fail it and `latest_date`; both
  failures are caught and logged, leaving no anchor and no volume check. Not
  tested.

### The backlog key for ad hoc SQL is what was touched

`service.py:385` keys an `ungoverned_sql` gap on the relations the SQL read.
Every uncovered question against `fct_orders` lands in one backlog row with an
`any_value` sample question. The design keys gaps on what was missing; this is
the most informative gap kind and it has the least useful key. The `users`
count is also 1 whenever auth is `none` or one token is shared.

### State and telemetry assume one long-lived process

The number-check pool lives in memory, keyed on `Mcp-Session-Id`, and falls
back to one shared `default` key when the header is absent. The telemetry
writer flushes from a daemon thread every five seconds and drops a batch on a
write failure. The design names Cloud Run. Not tested, but scale to zero or a
second instance would lose the pool, and a background thread is the kind of
thing that stalls when CPU is throttled between requests. The gap flywheel is
the second value claim and it rides on best-effort delivery.

## The load-bearing assumption

The chatbot is a faithful courier. It passes the user's words verbatim, relays
every disclosure, and calls `log_answer`. In BYO mode each of those is a
request, because the server sees neither the user's words nor the final reply.

A trap that did not fire leaves no trace. No mart can report the bypass rate,
so the logs will not show this failing; capture rate is observable and bypass
is not.

## What was traded away

Chosen: no model in the core path, so traps are phrase lists; a write-only
log, so no pins and no verified queries yet.

Not chosen: the eval expectations are snapshots of Understory's own output,
with at most four items marked verified. A 100% deterministic pass guards
regression, not truth. The live numbers are single passes over 23 items, and
the ablation ran on five items picked for their variance.

## First thing to break

The second or third turn of a friendly user's first conversation. "Break that
down by country" carries no trap phrase, and "how did that change" produces a
delta the number check rejects.

## The strongest alternative

Own the loop: ship the harness as the product, on Slack, with the connector as
a secondary surface.

- For it: the ablation in `harness-last-step-2026-09-22.md` went from 15/25 to
  25/25 once the check was structural. Code would see the user's words and
  could append disclosures itself instead of asking for them.
- Against it: about 3 cents a question on Sonnet, and adoption friction outside
  the chatbot people already use.

BYO is the right distribution. The confidence claim is only true in the owned
loop today. The way to narrow that without a model call is to key enforcement
on what the server does see: a spec naming a non-preferred candidate of a
collision gets a disclosure whatever the question text says.

## The spec-keyed disclosure

Added 2026-10-06. The matcher asks "did the user say an ambiguous word?",
which the server can only learn from the model. The rule asks "did the spec
land on a metric with a known confusable sibling?", which the server sees for
itself.

Today `_check_collision` returns early when no phrase is found in
`spec.question`. The rule adds a branch for that case:

- **Prefer traps.** A spec naming a candidate other than the preferred one gets
  a disclosure saying what it is and what the default reading would have been:
  "This is Gross Revenue, before discounts and refunds. 'Revenue' on its own is
  read as Net Revenue."
- **Ask traps.** A spec naming a candidate with no clarification choice gets a
  disclosure carrying the trap's `why`: "This is Margin Rate, a percent, not
  Gross Margin in dollars."
- **The preferred candidate** gets nothing. It is the default reading.
- **Dimension roles** follow the same rule.

No swap and no ask, because the user may really have said "gross". If they
did, the cost is one redundant sentence. If they did not, a silent wrong
reading becomes a disclosed one. The default window and the volume check
already work this way, keyed on the spec and the data; collisions are the one
part of the registry that depends on the model's copy of the question.

Two things it buys beyond the sentence. The follow-up turn is covered, because
the metric is still in the spec when the trap word has left the question. And
bypass becomes countable: with a distinct source on these disclosures, a mart
can count specs that named a non-preferred candidate with no phrase present,
an upper bound on a rate that cannot be measured at all today.

What it does not fix:

- The ask is not restored. Alpenglow's margin question becomes a disclosed
  answer, not a clarification. Asking whenever a candidate appears would
  over-ask everyone who typed "margin rate", so the disclosure is the floor.
- A metric outside the candidate set ("revenue" read as average order value)
  fires nothing, as now.
- Unanswerable traps have no spec shape to key on and stay phrase-only.
- The model still has to relay the disclosure.

Golden items that expect a clean answer for an explicitly named non-preferred
metric will need the new disclosure. It also settles part of the deferred
"where does the gentle guidance live" decision in favour of disclosures.

## Testing whether it works

Three stages, cheapest first. The first says whether the problem happens
often enough for the fix to be measurable.

### 1. The bypass rate today

The harness knows what the server never does: the user's real words, from the
golden item. For every `query_metrics` call in a live trace, run the trap
check twice, once with the `question` the model sent and once with the golden
question swapped in. A trap that fires only on the second run is a bypass.

That gives a base rate per model and per mode on the existing single-turn
items, with no new feature. Expect it to be low there, since the tool
docstring asks for the question verbatim.

### 2. The condition where it should fail

Multi-turn items, which the sets do not have. `run_question` already takes
`message_history`. Three kinds, about ten items on one tenant to start:

- **Carry-over.** The trap word is in turn 1 only ("revenue last quarter?",
  then "split that by country").
- **Synonym.** "Top line", "sales", where a model is most likely to tidy the
  wording.
- **Explicit.** The user really says "gross revenue". These measure noise,
  not coverage.

Run the stage 1 replay on these too.

### 3. The rule off and on

Behind a tenant switch, same items, `--repeat 5`, both modes, Sonnet and
Haiku. Roughly 400 runs.

| measure | what it says | want |
|---|---|---|
| silent wrong-reading rate | the reply gives a non-preferred candidate's number, the user's words were ambiguous, and the reply never names the candidate | falls toward zero |
| relay rate | share of the new disclosures that reach the reply | high; it caps the benefit |
| first-turn answer rate, explicit items | whether the extra sentence breaks anything | unchanged |
| extra queries per item | whether the model re-queries the preferred metric after reading the disclosure | flat on explicit items |
| output tokens per item | cost of the sentence | small |

Silent wrong-reading rate is the headline. Extra queries is the side effect to
watch: a model told "revenue on its own is read as Net Revenue" may go and
fetch net, which is right on a carry-over item and wrong on an explicit one.

Decide before running: ship if silent wrong readings on carry-over and synonym
items drop clearly and the explicit items stay within run-to-run noise. If
stages 1 and 2 show a bypass rate near zero even across turns, efficacy cannot
be shown and the rule is cheap insurance, worth keeping for the counter.

What this cannot test: with a real connector the log holds the model's copy of
the question, never the user's, so the mart count is only an upper bound.
Ground truth from friendly users means shared transcripts labelled by hand.

## Results

Run 2026-10-06 and 2026-10-07 on branch `spec-keyed-disclosure`, which holds
the oracle replay (`harness/replay.py`), the rule behind
`checks.spec_disclosures` (default off), ten multi-turn items for alpenglow
(`golden/multiturn.yml`: 4 carry-over, 3 synonym, 3 explicit, numbers
unverified), and `eval --spec-disclosures off|on|both`. All of it alpenglow
only. About $13.50 in total.

The replay labels each bypass by what was lost: a refusal, an ask, a swap, or
only the sentence. The first three are counted as material.

### Base rate, rule off, one pass, Sonnet

| set | mode | passed | items with a material bypass |
|---|---|---|---|
| multi-turn (10) | harness | 10/10 | 1 |
| multi-turn (10) | BYO | 7/10 | 3 |
| trap (11) | harness | 10/11 | 1 of 8 scored |
| trap (11) | BYO | 10/11 | 1 of 8 scored |

Bypass happens on a single turn too: `returns_prefer_april_2025` lost the
returns swap in both modes, and in harness mode the reply gave refunds without
naming the reading. The realistic set was not run.

### Rule off against on, multi-turn, five repeats, 50 item runs per cell

Harness mode:

| measure | Sonnet off | Sonnet on | Haiku off | Haiku on |
|---|---|---|---|---|
| passed | 47/50 | 49/50 | 29/50 | 44/50 |
| material bypasses | 10/49 | 5/50 | 17/50 | 12/50 |
| silent wrong readings | 0/39 | 0/40 | 0/40 | 1/40 |
| new disclosures relayed | n/a | 37/40 | n/a | 23/52 |
| first-turn answer rate | 84% | 88% | 74% | 82% |
| extra queries per item | 0.33 | 0.16 | 0.52 | 0.36 |
| cents per item | 3.59 | 3.44 | 2.07 | 1.98 |

BYO mode:

| measure | Sonnet off | Sonnet on | Haiku off | Haiku on |
|---|---|---|---|---|
| passed | 43/50 | 39/50 | 33/50 | 36/50 |
| material bypasses | 21/50 | 15/50 | 21/50 | 19/50 |
| silent wrong readings | 0/40 | 0/40 | 0/40 | 0/40 |
| new disclosures relayed | n/a | 65/65 | n/a | 45/63 |
| first-turn answer rate | 92% | 82% | 76% | 76% |
| extra queries per item | 0.56 | 0.36 | 0.34 | 0.26 |
| cents per item | 4.27 | 4.82 | 1.95 | 1.90 |

### Reading them

- **Bypass in BYO is the finding.** With the rule off, 42% of multi-turn item
  runs lost a swap or an ask on both models. Under the harness it was 20% on
  Sonnet and 34% on Haiku. The courier assumption fails often, across turns,
  on the mode the product ships in.
- **The rule relays.** Sonnet passed on every new disclosure in BYO and 92%
  under the harness. Haiku managed 71% and 44%.
- **Pass rates do not move one way.** The harness cells improved, Haiku by a
  lot. BYO Haiku barely moved. BYO Sonnet got worse: synonym items went from
  12/15 to 8/15, first-turn fell ten points, and cost rose about 13% on longer
  replies.
- **Explicit items were untouched**: 15/15 in every BYO cell, 14 or 15 of 15
  under the harness. The sentence costs nothing where the user was explicit.
- **The headline measure had nothing to show.** Silent wrong readings were
  zero in every baseline. A model that picks gross revenue says "gross
  revenue", and the definition does not count that as silent. It also misses
  a skipped ask whose reply names the candidate.

By the rule set before running, efficacy is not shown, and the switch stays
off. The pass score checks for the preferred metric's numbers and the rule
never swaps, so it was never going to repair a bypass, only label one.

Not examined, and needed before trusting either movement: why Sonnet's synonym
items got worse in BYO with the rule on, why Haiku's harness pass rate rose
from 29 to 44, and why the bypass count itself falls when the rule only adds a
sentence. At 15 to 20 runs per kind any of these could be noise. The traces
are in `tenants/alpenglow/.evals/`, which is not in git.

The four bypasses that recur: `returns_context_then_month` (the returns swap,
including all five Sonnet harness runs with the rule on),
`board_deck_revenue_then_number`, `revenue_then_by_country`, and the margin ask
on `margin_context_then_quarter`.

### What follows

The lost swap or ask is the problem, and a disclosure does not restore it. The
lever to try next is the `question` the model sends on a follow-up turn: a
tool description that asks for the earlier wording the follow-up depends on,
or a separate field for it. The replay now measures that directly, at about $3
for a both-modes pass on Sonnet.

Two things the build left open: the spec-keyed source is not written to
telemetry (no event carries disclosure sources; it is a Parquet schema change
and new staging columns), and the `both` arm of `--spec-disclosures` is now
exercised end to end by these runs but has no test beyond arm selection.

## Order to fix before friendly users

Item 1 was written before the results above. The spec-keyed disclosure is
built and off; what the results ask for first is the follow-up `question`.

1. Require `question`, and add the spec-keyed disclosure.
2. `log_answer`: accept arithmetic over sourced numbers (difference, ratio,
   percent change, sum), scope owed disclosures to the current question, and
   have status reflect them.
3. Move the tool bodies to `asyncio.to_thread`.
4. Lock DuckDB external access at connect, review `deny_relations` per tenant,
   and add the BigQuery bytes cap.
5. Add multi-turn golden items.
