# Closing step 4: the report, BYO mode, two tiers, and the volume check

2026-09-21. What landed to close the realistic set (design section 14, step 4),
what the fake data taught while building the volume check, and the first live
numbers in both modes on both tiers.

## A merge that missed main

PR #7 (`ratio-manifests`) was merged into `realistic-set` twelve minutes after
`realistic-set` merged into main, so its one commit never reached main. Nothing
in git or GitHub flags that shape: both PRs show merged. PR #8 carried it over.
Worth a habit: after merging a stacked PR, check `git log main..<branch>` for
the branches it was stacked on.

## The report

`first_turn_answer_rate` is the headline: the share of items a correct run
answers whose first turn came back resolved with the right numbers and
disclosures and no ask in between. An item that is right only after a
clarification counts against it, which is the point of the number; the two
`revenue` asks and the `units` ask in the sets do exactly that.
`over_refusal_rate` is the share of the same items that ended refused or with
nothing resolved. Both rates leave out items a correct run refuses, and both
break down by `kind`, so the report shows the over-refusal items' own rate
before a prompt change shows up anywhere else.

The deterministic runner scores the same two fields, so CI carries the headline
too. There it is a property of the server and the golden set, not of a model:
an ask is an ask whoever sends the spec.

## BYO mode

The MCP server's instructions and the seven tool descriptions moved into
`server/surfaces.py`, and `build_agent(byo=True)` builds the harness agent from
those two strings and nothing else: the connector instructions are the whole
system prompt and the tool docstrings are blanked so the MCP description is the
whole tool documentation. Same tool functions, same session, same trace. The
only thing the fake connector cannot copy is a real host's own scaffolding
around tool calls, which is what the manual smoke test through each connector
is for.

## The volume check

A number over a period whose rows only partly arrived is a plausible wrong
number the semantic layer cannot see, and the fake data has two such periods:
bristlecone's POS feed outage (a week of a weekly feed loaded at a quarter) and
white_cube's product events outage (two days of a daily feed loaded at 30%).
The check reads row counts per day on each time dimension a query touches,
once per five minutes per dimension, and discloses a period inside the window
that holds far fewer rows than its neighbours. It never changes the number.

Getting it to fire on those two and nothing else took three rules, each
learned from a false positive:

1. **Judge a bucket against the same weekday.** The first rule compared each
   day with the days around it and fired on nearly every weekend in the B2B
   tables (deals, invoices, shipments), where Saturday is a third of Tuesday
   by design. Comparing Sundays with Sundays removed all of those.
2. **Baseline on both sides.** Every series ramps up from nothing at the start
   and a few tail off at the end (payments scheduled past the cutoff). With
   neighbours only on one side, the ramp looked like a dropout. The baseline
   is now the smaller of the medians before and after, with at least two
   neighbours on each side, so only a dip between two healthy stretches fires.
3. **Two days, or one week.** After the first two rules the daily tables still
   flagged one day here and there: 25 December, 1 January, Memorial Day,
   Labor Day, Thanksgiving. The fake B2B calendar has holidays and a holiday
   is indistinguishable from a one-day outage by row count alone. A daily
   dropout is reported only as a run of two or more days; a weekly or coarser
   feed reports a single low bucket, because one bucket is a whole week. The
   cost is a real one-day outage on a daily feed, which the check will miss.

A baseline under twenty rows is not judged at all; returns at ten a day swing
by half on ordinary days.

Two faults in the ground truth the check cannot see, and one it half sees:

- A **loading delay** is invisible once the rows have landed. Staging keeps the
  latest `_loaded_at` per key and a static warehouse has all of them. Showing
  it needs an as-of build of the fake data (rows with `_loaded_at` after the
  as-of instant left out), which fake_companies does not have. With that, the
  existing anchor logic would already disclose it: the lagging table's latest
  date is earlier, and a derived metric anchors to the earliest.
- **Duplicate rows** are removed by staging's dedupe on `_loaded_at`.
- The **product events outage** is plain on `product_events` (934 rows against
  about 2,800) and invisible on `dau` and `wau`, whose mart is one row per user
  per day: a user with one surviving event still counts as active. A row-count
  check cannot see that. Catching it needs a per-metric expectation, which is
  roadmap 1.4 territory.

So `fault` items exist on two tenants, two each, and expect the disclosure by
its date and the word "incomplete". Alpenglow and meridian have no fault the
marts can show.

## Fill reorders

The first `fill` after the row-sorting commit reordered most numbers lists in
bristlecone and white_cube. That commit landed after the last fill, so the
files still carried MetricFlow's arbitrary order; this fill is the first in the
canonical order and a second fill changes nothing. Scoring is order-agnostic,
so nothing about the sets' meaning changed.
